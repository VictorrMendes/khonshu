# ADR-012 — Execution como Unidade Canônica de Runtime; Mission como Agregação

**Status:** Accepted
**Date:** 2026-07-02
**Deciders:** Victor Mendes
**Relacionado:** ADR-001, ADR-006, ADR-007, ADR-008, ADR-009, ADR-011 (referenciado em código, nunca formalizado)

---

## Contexto

Uma auditoria arquitetural completa do Khonshu (2026-07-02) e a investigação de um bug aparentemente pequeno — a página `/artifacts` sempre vazia — revelaram que o projeto hoje mantém **dois runtimes de execução independentes, evoluindo em velocidades diferentes**, sem elo entre si:

**Pipeline antigo** (ADR-001/ADR-007), usado por Scheduler/Inbox e pelo sistema de Missões:
```
Mission → PlanProvider → ExecutionPlan → PlanValidator → MissionStep[] → StepExecutor → tool.fn() → output
```

**Pipeline novo** (referenciado em código como "ADR-011: Tool-First Architecture", nunca documentado formalmente), usado pelo endpoint de chat (`/orchestrator/{id}/stream`), hoje o único caminho que o frontend efetivamente chama:
```
Execution → StrategyPlanner → ExecutionPlanner → ExecutionOptimizer → CapabilityResolver → IRCompiler → ExecutionStep[] → ExecutionRuntime → Scheduler → Dispatcher → Driver
```

Evidências concretas de que isso já é dívida técnica ativa, não apenas um risco teórico:

- `MissionEngine.add_artifact()` (`engines/mission/engine.py:345`) é o único ponto que grava em `mission_artifacts` — e não tem nenhum chamador em todo o backend. A funcionalidade de Artifacts está morta porque foi escrita para o pipeline errado.
- `models/execution.py`'s `Execution` tem `workspace_id`, mas **nenhuma FK para `missions`**. As duas árvores de dados não têm elo hoje.
- `kernel/execution/dispatcher.py`'s `RestDriver.execute()` é um stub: loga e comenta `# Here we would make an HTTP request`. Não seta `ExecutionStep.output`, não transiciona status para `COMPLETED`. O runtime novo hoje **descreve** execução, não **executa**.
- `kernel/orchestrator/capability_resolver.py` falha silenciosamente (loga um warning e segue) quando uma capability não existe — sintoma do mesmo problema de fundo: peças do sistema novo foram construídas sem uma base sólida por baixo.
- `SchedulerEngine`/`InboxEngine` (ADR-008) chamam `mission_engine.create()` via evento — o pilar "Khonshu age sem o usuário pedir" depende inteiramente do pipeline antigo continuar funcionando.

Sem uma decisão explícita, qualquer nova feature (como um pipeline de Artifacts) corre o risco de ser construída sobre a árvore errada e morrer quando a outra se tornar a oficial — exatamente o que já aconteceu uma vez.

---

## Decisão

### 1. `Execution` é a única entidade que executa

Todo processamento de uma ação real — chamar uma tool, uma capability, um workflow n8n — acontece dentro de uma `Execution`/`ExecutionStep`. O conjunto de estados já modelado em `models/execution.py` (`PENDING, READY, WAITING, WAITING_INPUT, WAITING_APPROVAL, WAITING_EVENT, BLOCKED, PAUSED, RUNNING, ROLLBACK, COMPLETED, FAILED, TIMEOUT, RETRYING, CANCELLED`) é adotado como a máquina de estados canônica de runtime. `Mission` deixa de ter seu próprio ciclo de execução.

### 2. `Mission` vira agregação + planejamento — não runtime

`Mission` mantém: `intent`/objetivo, prioridade, e a responsabilidade de **planejar** (gerar as `Execution`s necessárias a partir da intenção). O aparato de planejamento já existente (`PlanProvider`, `ExecutionPlan` versionado com `superseded` para replanejamento — ADR-001; `PlanValidator` checando permissões/parâmetros antes de qualquer coisa rodar — ADR-006) **migra de alvo**: em vez de produzir `MissionStep[]`, passa a produzir `Execution`(s) vinculadas à Mission. Nenhuma `Execution` sai de `PENDING` sem passar pela validação equivalente ao `PlanValidator` atual.

`Mission.status` deixa de ser um campo transicionado manualmente em paralelo. Passa a ser **derivado** do estado agregado das `Execution`s filhas (ex.: `running` se qualquer filha está `RUNNING`; `completed` se todas estão `COMPLETED`). Isso elimina uma segunda fonte de verdade sobre "o que está acontecendo agora" e torna `Mission.requires_approval` redundante — a aprovação já existe em granularidade mais fina (`ExecutionStep.approval_required`), então esse campo em `Mission` é candidato a remoção quando a migração terminar.

### 3. `Execution.mission_id` é opcional (nullable)

```
Execution
    mission_id  UUID | NULL   ← FK para missions.id
```

Nem toda execução pertence a uma missão. Uma pergunta simples do usuário ("quanto é 2+2?") gera uma `Execution` avulsa, sem `Mission`. Uma intenção complexa ("planeje minha viagem") gera uma `Mission` que por sua vez gera múltiplas `Execution`s vinculadas a ela. Isso é estritamente mais flexível que o modelo atual, em que tudo obrigatoriamente passa por uma `Mission`.

### 4. Artifacts pertencem à `Execution`, nunca à `Mission`

Quem produz evidência é a execução, não o agregador. `MissionArtifact` é renomeado/relocado para referenciar `execution_id` (obrigatório) em vez de `mission_id`. Uma `Mission` que queira listar seus artifacts consulta através das suas `Execution`s filhas — não os possui diretamente.

### 5. Conclusão de eventos via Domain Events, não chamada direta

Em vez de um componente chamar `mission_engine.add_artifact(...)` diretamente (o erro original), a transição de uma `Execution`/`ExecutionStep` para `COMPLETED` ou `FAILED` publica um evento de domínio (`execution.completed`, `execution.failed`, `execution.step.completed`) no `EventBus` já existente (`kernel/events/bus.py`, mesmo canal `khonshu.events` usado por `mission.*`). Um `ArtifactObserver` — a ser implementado — subscreve a esses eventos, inspeciona `ExecutionStep.output` e decide se há artifact a extrair, publicando-o no repositório de artifacts. Nenhum componente de execução precisa saber que artifacts existem.

Nota de implementação: `kernel/events/domain_events.py` já contém uma hierarquia de eventos estilo CloudEvent (`ExecutionStartedEvent`, `StepStartedEvent`, `ApprovalRequestedEvent`, `CapabilityDiscoveredEvent`) que não é referenciada em nenhum outro lugar do código. Antes de desenhar um novo conjunto de tipos de evento do zero, essa hierarquia deve ser revisada — é provavelmente uma tentativa anterior desta mesma ideia, abandonada antes de ser conectada ao `bus.py`.

### 6. `ExecutionRuntime` precisa executar de verdade antes de qualquer coisa acima ser testável

`Dispatcher`/`Driver` (`kernel/execution/dispatcher.py`) precisam deixar de ser stub: fazer a chamada real (inicialmente via `n8n_core`, que já tem manifest e um driver REST parcialmente escrito), popular `ExecutionStep.output` com o retorno real, e transicionar o status corretamente para `COMPLETED`/`FAILED`. Sem isso, nenhuma das decisões acima (eventos de conclusão, `ArtifactObserver`) tem o que observar.

### 7. Critério de saída para aposentar `MissionEngine`/`StepExecutor`

O pipeline antigo só pode ser removido depois que:
- `SchedulerEngine` e `InboxEngine` forem repontados para criar `Execution` (com `mission_id` quando aplicável) em vez de chamar `mission_engine.create()` diretamente.
- O papel de planejamento/validação (`PlanProvider`/`PlanValidator`/replanejamento com `superseded`) tiver um equivalente funcional no lado `Execution`.

Até lá, os dois pipelines coexistem conscientemente — a diferença em relação ao estado atual é que essa coexistência passa a ser uma fase de migração declarada, com critério de saída, e não um acidente de duas frentes de desenvolvimento que não se falam.

## Alternativas Consideradas

**Manter os dois pipelines permanentemente com uma camada de tradução entre eles.**
Rejeitada. Dobra a superfície de manutenção — exatamente o tipo de dívida técnica exponencial que motivou este ADR. Toda feature nova (como Artifacts) teria que decidir, caso a caso, para qual pipeline foi escrita.

**Tornar `Mission`/`StepExecutor` o pipeline canônico e tratar `Execution` como um experimento a descartar.**
Rejeitada. `Execution`/`ExecutionStep` já modela grafo de dependências (`depends_on`), retry policy estruturada e um conjunto de estados mais rico (`WAITING_EVENT`, `ROLLBACK`, `TIMEOUT`) do que `MissionStep`. É a base certa para o "Tool-First Architecture" (ADR-011, referenciado em código) que já é o caminho real do chat hoje. Reverter perderia esse investimento.

**Reescrita big-bang: apagar `Mission`/`StepExecutor` agora e portar tudo de uma vez.**
Rejeitada. `SchedulerEngine`/`InboxEngine` dependem do pipeline antigo hoje para o pilar "Khonshu age sem o usuário pedir" funcionar. Apagar antes de repontar esses gatilhos quebra missões agendadas/reativas silenciosamente. Além disso, `PlanValidator`/replanejamento não têm equivalente pronto no lado `Execution` — big-bang aqui significa perder validação de segurança (permissões, parâmetros) durante a transição.

## Consequências

**Positivas:**
- Uma única fonte de verdade sobre "o que está executando agora" — elimina a classe de bug que gerou o `MissionArtifact` morto.
- Execuções avulsas (sem `Mission`) tornam-se um conceito de primeira classe, em vez de forçadas a existir dentro de uma Mission artificial.
- Artifacts (e qualquer outra funcionalidade orientada a "o que uma execução produziu") passam a funcionar automaticamente para qualquer capability nova, sem lógica específica por integração.
- `Mission.status`/`requires_approval` deixam de ser uma segunda máquina de estados a manter sincronizada manualmente.

**Negativas:**
- Migração real, de múltiplas fases, tocando persistência (nova FK, mover a tabela de artifacts), runtime (`Dispatcher`/`Driver` reais) e o sistema de eventos.
- O aparato de planejamento/validação (`PlanProvider`, `ExecutionPlan` versionado, `PlanValidator`) precisa ser portado deliberadamente para o lado `Execution` — não é um "apagar e esquecer", é trabalho de design adicional que este ADR não especifica em detalhe (ver Questões em Aberto).
- Durante a migração, os dois pipelines continuam coexistindo — o risco de divergência não desaparece no dia em que este ADR é aceito, só passa a ter prazo de validade e critério de saída.

---

## Roadmap de Migração Proposto

1. **Completar o `ExecutionRuntime`**: `Dispatcher`/`RestDriver` executando de verdade via `n8n_core`, populando `ExecutionStep.output` e transicionando status corretamente. (Pré-requisito de tudo abaixo — sem isso nada é testável ponta a ponta.)
2. **Adicionar `Execution.mission_id` (nullable)** — migration Alembic, sem quebrar dados existentes.
3. **Portar o papel de planejamento**: decidir e implementar como `PlanProvider`/`PlanValidator` (ou um equivalente) passam a gerar/validar `Execution`s em vez de `MissionStep`s.
4. **Introduzir eventos de conclusão** (`execution.completed`, `execution.failed`, `execution.step.completed`) no `EventBus` existente, revisando primeiro a hierarquia CloudEvent já presente e não utilizada em `kernel/events/domain_events.py`.
5. **Mover `MissionArtifact` → referenciar `execution_id`**; implementar `ArtifactObserver` subscrevendo aos eventos de conclusão.
6. **Tornar `Mission.status` derivado** do estado agregado das `Execution`s filhas; avaliar remoção de `Mission.requires_approval`.
7. **Repontar `SchedulerEngine`/`InboxEngine`** para criar `Execution` (com `mission_id`) em vez de chamar `mission_engine.create()` diretamente.
8. **Aposentar `MissionEngine.run()`/`StepExecutor`** somente depois que os passos 1–7 estiverem validados em produção.

---

## Questões em Aberto (fora do escopo deste ADR)

- Forma exata como `ExecutionPlan`/versionamento/`superseded` mapeia para o lado `Execution` — decisão de design a ser tomada no passo 3 do roadmap, não aqui.
- Heurística de extração do `ArtifactObserver` por tipo de capability (quando `output` vira um artifact vs. quando é só um valor de retorno comum) — decisão de implementação, não arquitetural.
- Se o conjunto de `ExecutionStatus` atual (15 estados) deve ser reduzido/simplificado ao ser adotado como canônico, ou mantido como está.
- Se `MissionStep`/`mission_steps` é removido ou mantido como histórico read-only das execuções antigas após a migração.
